本技能接收当前对话上下文和代码库理解，产出规格说明（你可能称这种文档为 PRD）。请勿向用户访谈——只需综合你已知的信息即可。

Issue 追踪器和分类标签词汇表应该已经提供给你——如果没有，请运行 `/setup-matt-pocock-skills`。

## 流程

1. 如果你尚未探索代码库，请先探索以了解当前状态。在整个规格说明中使用项目的领域术语，并尊重新涉及区域中已有的 ADR（架构决策记录）。

2. 勾勒出你用来测试该功能的接缝（seam）。应优先采用现有接缝，而非新建接缝。尽可能选择最高层次的接缝。如果确实需要新接缝，请在你能够到的最高点提出。代码库中的接缝越少越好——理想数量为一个。

与用户确认这些接缝是否符合预期。

3. 使用下方模板撰写规格说明，然后将其发布到项目 Issue 追踪器。打上 `ready-for-agent` 分类标签——无需进一步分类。

<spec-template>

## 问题陈述

从用户视角描述用户面临的问题。

## 解决方案

从用户视角描述问题的解决方案。

## 用户故事

一个长长的、带编号的用户故事列表。每个用户故事应按以下格式编写：

1. 作为 <角色>，我想要 <功能>，以便 <收益>

<user-story-example>
1. 作为手机银行客户，我想要查看我账户的余额，以便对消费做出更明智的决策
</user-story-example>

这份用户故事列表应极为详尽，覆盖该功能的所有方面。

## 实现决策

已做出的实现决策列表。可以包括：

- 将要构建/修改的模块
- 将要修改的那些模块的接口
- 开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

请勿包含具体文件路径或代码片段。它们很可能很快就会过时。

例外：如果原型中产出了一个代码片段，其表达能力比文字描述更精确地编码了某个决策（如状态机、reducer、schema、类型结构），可以将其内联到相关决策中，并简要注明其来自原型。精简到富含决策的部分——不是可运行的演示，只保留关键部分。

## 测试决策

已做出的测试决策列表。包括：

- 对什么是好的测试的描述（只测试外部行为而非实现细节）
- 哪些模块将被测试
- 测试的先前参考（即代码库中类似类型的测试）

## 不在范围内

描述本规格说明中不包含的内容。

## 补充说明

关于该功能的任何补充说明。

</spec-template>
